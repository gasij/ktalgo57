# Планировщик маршрута курьера

Курьер выезжает со склада, развозит заказы по городу и до конца смены возвращается обратно.
Заказов больше, чем можно успеть, у части из них есть дедлайн. Программа выбирает,
**какие заказы везти и в каком порядке**, чтобы получить максимальную суммарную ценность.
При этом каждый выбранный заказ доставляется не позже своего дедлайна, а курьер возвращается
на склад не позже конца смены.

Проект продолжает задачу из контрольной точки 7 («маршрут дрона с ограниченным зарядом»).
Там нужно было добраться из A в B, здесь — пройти через несколько обязательных точек, выбрать
из них подмножество и порядок обхода. На этом переходе подход принципиально меняется: см.
[архитектурное решение 4](#ар-4-в-состоянии-dp-хранится-одно-число-а-не-измерение-по-времени).

## Постановка задачи

**Вход:**

- **Дорожная сеть** — ориентированный граф: вершины — перекрёстки и адреса, дуги — дороги
  со временем проезда в минутах (целое, ≥ 0). Дорога по умолчанию двусторонняя, бывают
  односторонние.
- **Склад** — вершина, где курьер находится в минуту 0.
- **Смена** — `T` минут: к минуте `T` курьер должен вернуться на склад.
- **Заказы** — у каждого заказа есть:
  - адрес;
  - ценность (≥ 1) — приоритет или оплата, то, что максимизируется;
  - дедлайн (необязательный) — крайняя минута прибытия;
  - время передачи на месте.

**Выход:** последовательность заказов с временем прибытия на каждый адрес, полный путь
по улицам и список недоставленных заказов с причиной.

**Критерий:** максимум суммарной ценности. Если ценность одинаковая — более раннее
возвращение на склад.

**Допущения:**

- Время проезда не зависит от времени суток.
- Курьер один.
- Вместимость сумки не ограничена.
- Ждать на месте не нужно (у заказов нет нижней границы «не раньше»).

Как решение меняется при снятии каждого допущения — см.
[границы применимости](#границы-применимости).

## Запуск

Нужен .NET 10 SDK. Все команды выполняются из папки `project/`.

```bash
dotnet test                                                           # 42 теста
dotnet run --project src/CourierRouting.Cli                           # все демо-сценарии
dotnet run --project src/CourierRouting.Cli -- scenarios/01-city.json # один сценарий
dotnet run -c Release --project src/CourierRouting.Cli -- --bench     # рост времени от числа заказов
```

Сценарии хранятся в JSON в папке [scenarios/](scenarios/), формат описан в
[ScenarioLoader.cs](src/CourierRouting/Io/ScenarioLoader.cs). Для каждого сценария программа
печатает оптимальный план (DP) и план жадного алгоритма, а затем сравнивает их.

|---|---|
| `01-city.json` | Основной: 12 перекрёстков, односторонняя улица, 8 заказов, 4 из них с дедлайном. DP — ценность 19, жадный — 16 |
| `02-greedy-trap.json` | Ближний дешёвый заказ «съедает» время дальних ценных: жадный 6, DP 10 |
| `03-deadline-trap.json` | Жадный едет к ближнему несрочному заказу и опаздывает к срочному |
| `04-edge-unreachable.json` | Ни один заказ не выполним: показаны все четыре причины отказа |
| `05-edge-empty.json` | Заказов нет |
| `06-edge-single.json` | Один заказ, укладывается в смену ровно впритык |

## Алгоритм

Решение — **комбинация двух техник курса: графы (Дейкстра) и динамическое программирование**.

### Шаг 1. Сжатие графа: Дейкстра из каждой ключевой точки

Ключевые точки — склад и адреса заказов, всего не больше `k + 1`. Из каждого *различного*
ключевого перекрёстка запускается Дейкстра по всему городу
([TravelTimes.cs:39](src/CourierRouting/Planning/TravelTimes.cs#L39)).
Результат — матрица `(k+1)×(k+1)` кратчайших времён и деревья предшественников, по которым
потом восстанавливается путь по улицам. После этого шага планировщику сам граф не нужен.

### Шаг 2. DP по подмножествам заказов

Используется идея алгоритма Хелда — Карпа для задачи коммивояжёра, дополненная дедлайнами,
ограничением смены и выбором подмножества.

- **Состояние** `(mask, last)`: `mask` — битовая маска уже доставленных заказов, `last` —
  заказ, доставленный последним (курьер стоит у него).
- **Значение** `finish[mask, last]` — самая ранняя минута окончания передачи заказа `last`
  при условии, что доставлены ровно заказы `mask`, все их дедлайны соблюдены и до конца
  смены ещё можно вернуться на склад.
- **База:** `finish[{j}, j] = dist(склад, j) + service(j)`, если заказ `j` успевает к дедлайну.
- **Переход** ([DpRoutePlanner.cs:72-95](src/CourierRouting/Planning/DpRoutePlanner.cs#L72-L95)):
  из `(mask, last)` к заказу `next ∉ mask`:
  - `arrival = finish[mask, last] + dist(last, next)`;
  - переход допустим, если `arrival ≤ deadline(next)` и
    `arrival + service(next) + dist(next, склад) ≤ T`;
  - в `finish[mask ∪ {next}, next]` записывается минимум из старого значения и
    `arrival + service(next)`.
- **Порядок вычисления:** маски по возрастанию. Переход только добавляет биты, поэтому все
  пути в состояние рассмотрены раньше, чем оно само обрабатывается.
- **Ответ:** среди всех достигнутых состояний выбирается максимальная `value(mask)`, при
  равенстве — минимальное время возвращения. Пустой маршрут допустим всегда, поэтому ответ
  есть при любых данных.
- **Восстановление:** массив `previous[mask, last]` хранит предыдущий заказ, по нему порядок
  объезда восстанавливается с конца
  ([DpRoutePlanner.cs:145](src/CourierRouting/Planning/DpRoutePlanner.cs#L145)).

### Шаг 3. Сборка плана

[RouteBuilder.cs](src/CourierRouting/Planning/RouteBuilder.cs) повторно моделирует найденную
последовательность: считает время прибытия, проверяет дедлайны и смену, склеивает путь по
улицам и классифицирует недоставленные заказы. Этот общий код используют и DP, и жадный
алгоритм, поэтому их результаты проверяются одними и теми же правилами.

## Сложность

Обозначения: `V` — перекрёстки, `E` — дуги, `k` — заказы.

| Часть | Время | Память | Где в коде |
|---|---|---|---|
| Дейкстра, один запуск | `O((V + E) log V)` | `O(V)` | [ShortestPaths.cs:66-82](src/CourierRouting/Graph/ShortestPaths.cs#L66-L82) |
| Матрица времён | `O(k · (V + E) log V)` — не больше `k + 1` запусков | `O(k · V)` — деревья для восстановления пути | [TravelTimes.cs:35-43](src/CourierRouting/Planning/TravelTimes.cs#L35-L43) |
| DP | `O(2^k · k²)` | `O(2^k · k)` | [DpRoutePlanner.cs:102-117](src/CourierRouting/Planning/DpRoutePlanner.cs#L102-L117) |
| Сборка плана | `O(k + длина пути)` | то же | RouteBuilder |
| **Итого** | **`O(k · (V + E) log V + 2^k · k²)`** | **`O(V + E + k · V + 2^k · k)`** | |

**Откуда берутся эти оценки в коде:**

- **DP, время.** Три вложенных цикла — `mask` (`2^k`), `last` (`k`), `next` (`k`) — и
  переход `Relax` за `O(1)`, итого `O(2^k · k²)`.
- **DP, память.** Массивы `finish` (`int`) и `previous` (`sbyte`) по `2^k · k` элементов.
  При `k = 20` это около 21 млн ячеек, порядка 100 МБ.
- **Дейкстра.** Каждая дуга релаксируется один раз; куча без `decrease-key` с ленивым
  удалением устаревших записей хранит не больше `E + 1` элементов, отсюда `O(E log V)`.

**Что доминирует.** При реальных размерах (тысячи перекрёстков, до 20 заказов) первое
слагаемое мало, а DP растёт экспоненциально. Добавление одного заказа удваивает таблицу.
Замер на решётке 40×40 (1600 перекрёстков), смена 480 минут, Release:

| k | Дейкстры, мс | DP, мс | состояний DP |
|---|---|---|---|
| 12 | 5.7 | <1 | 49 152 |
| 16 | 6.9 | 4 | 1 048 576 |
| 18 | 8.3 | 16 | 4 718 592 |
| 20 | 8.3 | 90 | 20 971 520 |

Дальше — память: при `k = 25` таблица займёт ~4 ГБ, при `k = 30` — ~160 ГБ. Поэтому
`k > 20` ([DpRoutePlanner.cs:36](src/CourierRouting/Planning/DpRoutePlanner.cs#L36))
отклоняется явной ошибкой, а не падением по нехватке памяти.

## Архитектурные решения и их обоснование

### АР-1. DP по подмножествам, а не жадный алгоритм

**Решение.** Основной планировщик — точное DP. Жадный «ближайший сосед»
([GreedyRoutePlanner.cs](src/CourierRouting/Planning/GreedyRoutePlanner.cs)) реализован
только для сравнения.

**Почему не жадный.** Жадный выбор («ехать к ближайшему выполнимому заказу») всегда даёт
*допустимый* маршрут, но не оптимальный. Решение, выгодное локально (ближайший адрес),
может отнять время, которого потом не хватит. Контрпримеры, проверенные тестами
([GreedyVsDpTests.cs](tests/CourierRouting.Tests/GreedyVsDpTests.cs)):

- **`02-greedy-trap`.** Рядом со складом (5 мин) киоск ценностью 1; в другой стороне
  (30 мин) два офиса по 5; смена 75.
  - Жадный: киоск → офис-1 → обратно = 70 мин, ценность 6. На второй офис не хватает 5 минут.
  - Оптимум: оба офиса = 70 мин, ценность 10.
- **`03-deadline-trap`.** Ближний заказ без срока (5 мин), дальний — с дедлайном 10.
  - Жадный едет к ближнему и к дальнему прибывает в минуту 20 — поздно.
  - Оптимум: сначала дальний.
- **Случайные задачи.** На 1500 задачах жадный никогда не лучше DP и в заметной доле
  случаев хуже.
  В бенчмарке при `k = 20` он теряет около 15 % ценности.

Для монет жадный алгоритм корректен на канонических системах (КТ5), и это можно проверить.
Здесь аналогичного свойства нет: даже в задаче коммивояжёра без дедлайнов (частный случай
нашей) ближайший сосед может ошибаться сколь угодно сильно.

**Доказательство корректности DP.** Почему достаточно хранить одно число
`finish[mask, last]`:

1. **Будущее зависит только от состояния.** Что курьер может сделать дальше, зависит только
   от того, где он стоит (`last`), что уже доставлено (`mask`), и от текущего времени.
   История, как он сюда попал, не важна.
2. **Раньше — не хуже (доминирование).** Все ограничения — верхние границы времени: дедлайн
   и конец смены. Пусть два маршрута пришли в одно состояние в моменты `t₁ ≤ t₂`.
   - Любое продолжение второго выполнимо и для первого: все моменты прибытия сдвигаются на
     `t₂ − t₁` раньше, а верхние границы от этого не нарушаются.
   - Ценность маршрута равна `value(mask)` + ценность продолжения и от порядка внутри `mask`
     не зависит.
   - Значит, более поздний маршрут можно отбросить без потери оптимума.
3. **Отсечение корректно.** Состояние отбрасывается, если `done + dist(next, склад) > T`.
   Это безопасно: любой путь до склада через другие адреса не короче кратчайшего прямого
   (`dist` — кратчайшие расстояния, неравенство треугольника), а время передачи ≥ 0.
4. **Полнота.** Каждый допустимый маршрут — цепочка переходов из базы. Индукцией по `|mask|`:
   `finish` каждого состояния не больше времени любого допустимого маршрута, который в него
   приходит. Ответ перебирает все состояния и пустой маршрут, значит, оптимум не пропущен.

Корректность проверена и экспериментально: на 1500 случайных задачах DP совпал с полным
перебором всех упорядоченных подмножеств. Эталон использует свой Флойд — Уоршелл вместо
Дейкстры ([Reference.cs](tests/CourierRouting.Tests/Reference.cs)). Если в DP сохранять
самое *позднее* время вместо раннего, три теста падают — значит, тесты эту ошибку ловят.

### АР-2. Сначала сжать граф до k + 1 точек, потом DP — а не поиск по состояниям в полном графе

В КТ7 Дейкстра шла по состояниям `(перекрёсток, заряд)` прямо в графе города. Здесь так
тоже можно: состояние `(перекрёсток, mask)`. Но тогда состояний будет `V · 2^k` вместо
`k · 2^k`. При `V = 1600`, `k = 20` это 1,7 млрд против 21 млн — в 80 раз больше, и
каждое ещё и требует кучи.

Разделение на два независимых шага убирает `V` из экспоненциальной части. Это корректно:
между двумя доставками курьеру нет смысла ехать не кратчайшим путём — по доводу
доминирования из АР-1, прибыть раньше не хуже.

Кроме того, шаги разделены и в коде: `TravelTimes` можно заменить, например, на расстояния
из картографического сервиса, не трогая DP.

### АР-3. Дейкстра из k + 1 точек, а не Флойд — Уоршелл; список смежности, а не матрица

**Дейкстра против Флойда — Уоршелла.**

- Флойд — Уоршелл считает расстояния между *всеми* парами перекрёстков: `O(V³)` времени и
  `O(V²)` памяти. При `V = 1600` это ~4·10⁹ операций и 20 МБ ради матрицы, из которой
  нужна лишь `(k+1)²` часть.
- `k + 1` запусков Дейкстры: ~21 · 6240 · log 1600 ≈ 1,5·10⁶ операций. По замеру — 8 мс.
- Флойд — Уоршелл всё же используется в тестах как независимый эталон: там граф маленький,
  а простота важнее скорости.

**Список смежности против матрицы смежности.**

- Городской граф разреженный: у перекрёстка 2–4 соседа, `E ≈ 4V`. Список смежности занимает
  `O(V + E)` памяти, а Дейкстра перебирает только реальные дороги.
- С матрицей каждый шаг Дейкстры просматривал бы строку из `V` элементов, большинство из
  которых пустые: `O(V²)` на запуск и `O(V²)` памяти.
- В списке без дополнительных структур хранятся параллельные дороги и односторонние улицы.

Для ускорения используются ещё две мелочи:

- одинаковые адреса не требуют повторной Дейкстры
  ([TravelTimes.cs:35-43](src/CourierRouting/Planning/TravelTimes.cs#L35-L43));
- куча `PriorityQueue` из стандартной библиотеки без `decrease-key` используется с ленивым
  удалением устаревших записей.

### АР-4. В состоянии DP хранится одно число, а не измерение по времени

В КТ7 заряд был *частью ключа* состояния: `(станция, заряд)`. Там два критерия
конфликтовали: дешёвый путь мог прийти с меньшим зарядом, и ни один из двух путей не
доминировал над другим. Поэтому хранить приходилось оба.

Здесь время — одновременно и ресурс, и критерий доминирования: раньше всегда не хуже
(доказательство в АР-1, п. 2). А ценность целиком определяется ключом `mask`, поэтому
конфликта критериев нет, и время можно хранить как *значение*, а не как координату.

Это сокращает таблицу в `T` раз по сравнению с вариантом `dp[mask][last][время]`,
аналогичным КТ7: при смене 480 минут — в 480 раз.

У этого решения есть граница: оно перестаёт работать, если появятся окна «не раньше» без
права ждать или время проезда начнёт зависеть от момента выезда без свойства FIFO
(см. [границы применимости](#границы-применимости)).

## Отклонённые альтернативы

| Подход | Сложность | Почему отклонён |
|---|---|---|
| Полный перебор всех порядков всех подмножеств | `O(k! · k)` | Упорядоченных подмножеств ≈ `e · k!`: при `k = 12` — ~1,3·10⁹, при `k = 20` — ~7·10¹⁸. DP перебирает `2^k · k` состояний: разные порядки одного множества с одинаковым концом схлопываются в одно состояние. Перебор оставлен эталоном в тестах (`k ≤ 6`) |
| Жадный «ближайший сосед» | `O(k²)` | Не оптимален, контрпримеры выше (АР-1). Оставлен для сравнения |
| Жадный «максимум ценности за минуту» | `O(k²)` | Тоже не оптимален: ценный заказ рядом с дедлайном важнее, чем выгодный по отношению, но несрочный. Свойства жадного выбора нет |
| Рюкзак DP: ценность при бюджете времени | `O(k · T)` | Время на заказ не аддитивно: оно зависит от того, откуда курьер едет, то есть от порядка. Рюкзак модель не описывает |
| Дейкстра по `(перекрёсток, mask)` в полном графе | `O(V · 2^k · k · log)` | В `V/k` раз больше состояний (АР-2) |
| Флойд — Уоршелл для расстояний | `O(V³)` | Считает ненужные пары (АР-3). Используется в тестах как эталон |
| Матрица смежности | `O(V²)` памяти | Граф разреженный (АР-3) |
| BFS вместо Дейкстры | `O(V + E)` | Время проезда у дорог разное, BFS находит путь с минимальным *числом* дорог, а не минимальным временем |
| Ветви и границы, целочисленное ЛП, эвристики (2-opt, имитация отжига, муравьиные алгоритмы) | от экспоненты в худшем случае до полинома без гарантии | Нужны при `k ≫ 20`. Точные методы сложны в реализации (оценки, LP-релаксация), эвристики не гарантируют оптимум. Для `k ≤ 20` DP проще и точен |

## Пограничные случаи и некорректные данные

**Пограничные случаи.** Все обрабатываются, каждый закрыт тестом
([DpRoutePlannerTests.cs](tests/CourierRouting.Tests/DpRoutePlannerTests.cs)).

| Случай | Поведение |
|---|---|
| Заказов нет | Пустой маршрут, путь `[Склад]`, возврат в минуту 0 |
| Один заказ, ровно впритык по смене / на минуту не хватает | Доставлен / не доставлен с причиной «не укладывается в смену» |
| Дедлайн ровно в момент прибытия | Успел (`arrival ≤ deadline`) |
| Смена 0 минут | Доставляются только заказы на самом складе без времени передачи |
| Адрес не связан с сетью | Причина «недостижим» |
| Туда можно, обратно нельзя (одностороннее движение) | Причина «недостижим» — вернуться на склад невозможно |
| К дедлайну не успеть даже напрямую | Причина «дедлайн недостижим» |
| Ни один заказ не выполним | Пустой маршрут, у каждого заказа своя причина (`04-edge-unreachable`) |
| Несколько заказов по одному адресу; заказ на складе | Расстояние 0, лишних запусков Дейкстры нет |
| Маршрут проходит один перекрёсток несколько раз | Допустимо: состояние DP — заказы, а не перекрёстки |
| Ровно 20 заказов / 21 заказ | Решается / `ArgumentException` с объяснением |

**Некорректные и противоречивые данные.** Проверяются явно при создании задачи, а не
предполагаются корректными ([ValidationTests.cs](tests/CourierRouting.Tests/ValidationTests.cs)).

- **Отрицательное время проезда — отклоняется.** Оно ломает инвариант Дейкстры: извлечённая
  из кучи вершина больше не должна улучшаться. Кроме того, при отрицательном цикле
  «кратчайшего» пути нет вовсе.
- **Также отклоняются:**
  - отрицательные смена, дедлайн или время передачи;
  - ценность ≤ 0;
  - повторяющийся номер заказа;
  - адрес или склад, которых нет в сети;
  - битый JSON.
- **Циклы в графе — норма для города**, Дейкстра обрабатывает их без особой логики.
- **Защита от переполнения.** Суммы времени считаются в `long`.
- **Внутренняя проверка.** Если DP построит недопустимый маршрут (внутренняя ошибка),
  `RouteBuilder` это заметит и выбросит исключение, а не вернёт неверный план.

## Границы применимости

Что перестанет работать первым при изменении условий:

- **Число заказов растёт на порядки (сотни).** Первой ломается таблица DP — по памяти
  `2^k · k`, а не по времени. Дейкстры остаются дешёвыми. Нужен переход на эвристики
  с отказом от гарантии оптимума или на метод ветвей и границ, где экспонента остаётся
  только в худшем случае.
  - Промежуточный вариант: кластеризовать заказы по районам и запускать DP внутри
    кластера.
- **Город растёт на порядки (миллионы перекрёстков).** Растёт только шаг 1, линейно по
  `k`. Ускорить его можно двунаправленной Дейкстрой, A* с эвристикой по расстоянию на
  карте или предобработкой (contraction hierarchies).
- **Появились окна «не раньше»** (клиент дома только с 14:00).
  - Если ждать разрешено, DP остаётся корректным: прибывать раньше по-прежнему не хуже,
    курьер подождёт — `arrival = max(arrival, opens)`.
  - Если ждать нельзя, доминирование «раньше — не хуже» ломается, и время придётся делать
    измерением состояния, как заряд в КТ7.
- **Время проезда зависит от момента выезда (пробки).** Корректность сохраняется, пока
  выполняется свойство FIFO: выехав раньше, не приедешь позже. Без него ломаются и
  Дейкстра, и доминирование в DP.
- **Несколько курьеров.** DP по подмножествам обобщается: для каждого подмножества
  считается лучший маршрут одного курьера, затем подмножества делятся между курьерами —
  `O(3^k)`. На практике чаще используют эвристики.
- **Вместимость сумки.** Добавляется проверка суммарного объёма по `mask` — размер
  состояния не меняется.
- **Распараллеливание.**
  - Шаг 1 распараллеливается тривиально: `k + 1` независимых Дейкстр.
  - DP — узкое место: состояния с `|mask| = m` зависят только от `|mask| = m − 1`, поэтому
    параллелить можно внутри одного «слоя» по числу бит. Но вычислений на ячейку мало,
    упираться всё будет в пропускную способность памяти, а не в ядра.
- **Рекурсия.** В решении её нет: DP и Дейкстра итеративны, и глубина стека от размера
  входа не зависит. Рекурсивен только эталонный перебор в тестах (глубина ≤ `k + 1`,
  `k ≤ 6`).
