# Подготовка к защите

Шпаргалка для себя: сценарий демонстрации и ответы на вопросы из задания со ссылками на код.
Подробные обоснования — в [README](../README.md).

## Сценарий демонстрации (~3 минуты)

```bash
cd project
dotnet test                                                            # 1. все 42 теста зелёные
dotnet run --project src/CourierRouting.Cli -- scenarios/01-city.json   # 2. основной сценарий
dotnet run --project src/CourierRouting.Cli -- scenarios/02-greedy-trap.json      # 3. жадный хуже
dotnet run --project src/CourierRouting.Cli -- scenarios/04-edge-unreachable.json # 4. пограничный
dotnet run --project src/CourierRouting.Cli -- scenarios/07-invalid-negative.json # 5. некорректный ввод
dotnet run -c Release --project src/CourierRouting.Cli -- --bench      # 6. если спросят про масштаб
```

Что проговорить по ходу:

1. **`01-city`.** DP берёт F (дедлайн 25) первым, затем B (дедлайн 60).
   - Ценность 19 против 16 у жадного.
   - Жадный поехал к ближнему заводу (ценность 1) и из-за этого не успел к F.
2. **`02-greedy-trap`.** Ловушка понятна на пальцах: киоск рядом, но из-за него теряется
   второй офис.
3. **`04-edge-unreachable`.** Маршрут пустой, у каждого заказа своя причина:
   - X — изолированный адрес;
   - Y — одностороннее движение, туда можно, обратно нельзя;
   - Z — дедлайн раньше, чем можно доехать;
   - W — поездка туда и обратно длиннее смены.
4. **`07-invalid-negative`.** Отрицательное время проезда отклоняется явно: Дейкстра на нём
   некорректна.

Если спросят, почему в `02-greedy-trap` DP едет сначала к Офису-2, проезжая Офис-1: оба
порядка дают 70 минут и одинаковую ценность. При равенстве выбирается первый найденный,
порядок внутри ничьей не оптимизируется. Можно добавить третий критерий (например, сумму
моментов прибытия), но это отдельное DP-значение.

## Базовые вопросы

**1. Сложность вашей реализации и за счёт чего.**

`O(k·(V+E) log V + 2^k·k²)` по времени, `O(V + E + k·V + 2^k·k)` по памяти.

- **Первое слагаемое — Дейкстры** ([TravelTimes.cs:35-43](../src/CourierRouting/Planning/TravelTimes.cs#L35-L43)):
  - не больше `k+1` запусков, повторяющиеся адреса не пересчитываются;
  - каждый запуск — двоичная куча, каждая дуга релаксируется один раз.
- **Второе слагаемое — три цикла** `mask × last × next` в
  [DpRoutePlanner.cs:102-117](../src/CourierRouting/Planning/DpRoutePlanner.cs#L102-L117),
  переход за O(1).
- **Память DP** — два массива по `2^k·k`. В реальности доминирует именно DP: см. бенчмарк.

**2. Почему этот алгоритм, а не альтернатива.**

- **DP, а не жадный.** Жадный теряет ценность. Контрпримеры — `02`, `03`, `01`; на
  случайных данных в бенчмарке до ~15 %.
- **DP, а не перебор.** Перебор — `e·k!`, DP — `2^k·k`. Перестановки одного множества с
  одним концом схлопываются в одно состояние.
- **Дейкстра, а не Флойд — Уоршелл.** Флойд — `V³` ради ненужных пар перекрёстков.
- **Список смежности, а не матрица.** Граф разреженный.

**3. Пограничные данные.** Показать `04`, `05`, `06`. Пустой маршрут допустим всегда,
поэтому ответ есть при любых данных — недостижимость выражается пустым маршрутом и
причинами, а не исключением. Исключение бросается только на некорректный ввод и при
`k > 20`.

**4. Рекурсия.** В решении её нет: DP и Дейкстра итеративные, стек от входа не растёт.
Рекурсивен только эталонный перебор в тестах (глубина `k+1 ≤ 7`). Если бы DP писали
рекурсией с мемоизацией сверху вниз, глубина была бы до `k+1 ≤ 21` — не страшно. Страшен
был бы рекурсивный DFS по графу города: глубина до `V`, при сотнях тысяч вершин
`StackOverflowException`, который в .NET не перехватывается.

**5. Почему DP корректен.** Это ключевой вопрос, рассказывать по README, АР-1:

1. Будущее зависит только от `(mask, last, время)`.
2. Все ограничения — верхние границы, поэтому раньше не хуже: доминирование.
3. Ценность определяется только `mask`.
4. Отсечение по возврату корректно по неравенству треугольника для кратчайших путей.
5. Подтверждение: совпадение с перебором на 1500 случайных задачах. Мутационная проверка —
   если хранить позднее время, падают 3 теста.

Также полезно сравнить с КТ7 (АР-4): там заряд был в ключе состояния, потому что «дешевле»
и «больше заряда» конфликтовали. Здесь «раньше» — единственный критерий, поэтому время
хранится значением.

## Углублённые вопросы

**Изменение условий: что сломается первым.**

- **`k` вырос до сотен.** Первой ломается память DP (`k = 25` → 4 ГБ). Дальше нужны
  эвристики или метод ветвей и границ.
- **Окна «не раньше» без права ждать.** Ломается доминирование: время становится
  измерением состояния, как заряд в КТ7.
- **Пробки без свойства FIFO.** Ломаются и Дейкстра, и DP.
- **Изменения, которые решение выдерживает:**
  - город вырос — только шаг 1, линейно по `k`;
  - вместимость сумки — проверка по `mask`, размер состояния тот же;
  - окна «не раньше» с правом ждать — `max(arrival, opens)`.

**Есть ли более эффективный алгоритм.** Задача NP-трудная: она обобщает коммивояжёра,
поэтому полиномиального точного алгоритма не ждём.

- **Точные методы быстрее на практике:**
  - метод ветвей и границ с хорошей оценкой;
  - целочисленное ЛП (Orienteering Problem with Time Windows).
  Они сильно сложнее в реализации, а экспонента в худшем случае остаётся.
- **Эвристики** — 2-opt, имитация отжига, LNS. Полиномиальны, но без гарантии оптимума.
- **Экономия памяти в DP:**
  - хранить только слои `|mask| = m−1` и `m` — но тогда теряется восстановление пути;
  - убрать заведомо невыполнимые маски.

**Недопустимые данные.** Обрабатываются явно — см. README, раздел «Пограничные случаи и
некорректные данные».

- **Отрицательные веса.** Отклоняются в `RoadNetwork.AddRoad`. Если бы их нужно было
  поддерживать, понадобился бы Беллман — Форд `O(VE)` или Джонсон (перевзвешивание +
  Дейкстра). При отрицательном цикле кратчайшего пути нет.
- **Циклы в графе.** Норма для города, ничего не ломают.

**Распараллеливание и узкое место.**

- **Шаг 1** распараллеливается тривиально: `Parallel.For` по ключевым точкам.
- **DP — узкое место.** Ячейки слоя `|mask| = m` зависят только от слоя `m−1`, поэтому
  параллелить можно по слоям. Но работы на ячейку мало, и упор будет в пропускную
  способность памяти: 100 МБ таблицы не помещаются в кэш процессора.

**Какие ещё темы курса применимы.**

- **Бинарный поиск по ответу.** «Можно ли набрать ценность ≥ X» — монотонно по X. Но DP
  и так даёт максимум сразу, так что выигрыша нет.
- **Сортировка заказов по дедлайну.** Годится как эвристика, не как точный метод.
- **Скользящее окно.** Применимо, если заказы лежат на одной линии (улица-луч).
- **BST или куча по времени.** Нужны в онлайн-версии, когда заказы поступают в течение
  смены.
- **Рюкзак.** Подошёл бы, если бы время на заказ не зависело от порядка. Здесь зависит,
  поэтому не подходит.
